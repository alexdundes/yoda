O combinado antes do código

YODA é um framework document-first para desenvolver com agentes de IA. A documentação é a fonte de verdade operacional, scripts determinísticos garantem o combinado, e cada fase do trabalho passa pela sua autorização.

O problema

Contexto solto não governa trabalho

Um agente de IA competente ainda pode escolher a issue errada, implementar antes de entender, confundir intenção com autorização e terminar tecnicamente certo mas fora do que foi combinado. Modelo melhor reduz a frequência disso. Não elimina a categoria.

A causa raiz costuma ser a mesma: o contexto existe, mas não tem lugar. Ele mora numa conversa que acaba, num prompt que se perde, na cabeça de quem abriu a tarefa. Quando o contexto não está no repositório, em formato estável, cada nova sessão recomeça do zero e cada agente reinterpreta o combinado do seu jeito.

Pedir para o agente “seguir o contexto” não é processo. É desejo. Para virar processo, o contexto precisa ter lugar, ordem, entrada, saída, critério e autorização.

O que o YODA faz

Transforma o combinado em artefato

Antes de qualquer código, o trabalho vira uma issue em Markdown dentro do repositório, com contexto, objetivo, escopo, critérios de aceite, riscos e dependências. Essa issue é o contrato. O agente executa dentro dela, e o que ele fez fica registrado no próprio arquivo.

fonte de verdade

Documentação

A issue Markdown carrega metadado estruturado e contexto narrativo no mesmo arquivo. Vive no repositório, versionada e revisável como código.

árbitro

Scripts

Regra que não pode depender de interpretação vira comando determinístico: qual issue vem agora, qual fase pode começar, o que fica registrado.

executor

Agente

O agente lê o manual embarcado, segue o runbook que o script devolve e para no fim de cada fase para você autorizar a próxima.

O nome

YAML-Oriented Documentation & Agents

YODA é sigla de YAML-Oriented Documentation & Agents, e ela guarda uma reviravolta do próprio projeto.

No começo, o YAML era a estrutura de organização. O backlog inteiro vivia num arquivo TODO.<slug>.yaml, os registros de execução ficavam em arquivos YAML separados, e o Markdown era só o texto ao lado. Funcionava, e cobrava um preço: o estado de uma issue morava num arquivo, a narrativa em outro, e manter os dois em sincronia era trabalho manual que ninguém queria fazer. Quando divergiam, não havia como saber qual dos dois estava certo.

Hoje o Markdown é a fonte de verdade operacional, e o YAML continua ali — onde ele é bom. Ele mora no front matter da própria issue. Metadado estruturado e contexto narrativo passaram a ocupar o mesmo arquivo, e a pergunta “qual versão vale?” deixou de existir.

O nome ficou, e não por nostalgia. É o YAML do front matter que torna a seleção determinística possível: é dele que saem status, fase, dependências e prioridade, os dados que decidem qual issue vem agora sem depender da leitura interpretativa de ninguém. Por que resolve

Quatro garantias que um prompt não dá

Seleção determinística

Qual issue vem agora não é opinião do agente. É resultado de ordem natural, dependências declaradas e estado registrado. O mesmo backlog produz a mesma escolha, com qualquer agente.

Fronteira de fase

Uma fase por interação. O agente apresenta o entregável e para. Sem autorização explícita, não avança. Isso corta o “já que estou aqui, implemento também”.

Memória que sobrevive à sessão

Decisões, achados e transições ficam na issue, não no histórico do chat. Amanhã, outro agente ou outra pessoa continua de onde parou.

Rastro auditável

Cada transição de fase entra no log da issue com data e resumo. Dá para reconstruir depois o que foi decidido, quando, e com qual justificativa.

Como você usa

Você conversa. O agente executa.

Esta é a parte que mais confunde quem chega pela primeira vez, então vale dizer sem rodeio: os scripts em yoda/scripts/ são ferramentas do agente, não da pessoa. Você não precisa decorar comando nenhum.

O seu trabalho é dizer o que quer, ler o que o agente apresenta no fim de cada fase e autorizar o próximo passo. O agente cuida de descobrir qual comando rodar, quando rodar e o que fazer com a saída.

Você diz

“Vamos entrar no YODA Intake. Quero abrir uma issue para o problema de cache na listagem de pedidos.”

O agente faz
  1. Lê o manual embarcado em yoda/yoda.md.
  2. Executa o script de Intake e segue o runbook devolvido por ele.
  3. Revisa o backlog atual para não duplicar trabalho já previsto.
  4. Pergunta o que faltar, traduz a conversa em issue estruturada e cria o arquivo.
  5. Apresenta o resultado e para, esperando sua decisão.
Uma exceção O único comando que você digita é o instalador, uma vez por projeto. Tudo depois disso passa pelo agente. Se um agente pedir para você rodar um script do YODA, ele está fora do combinado — a única situação prevista é uma falha de coleta de issue externa que dependa da sua sessão autenticada.

Instalação

Um comando, uma vez

O instalador baixa o pacote, valida o checksum e já inicializa a estrutura com o seu developer slug — o identificador curto que vira prefixo das suas issues, como mynick-0001. 

# troque mynick pelo seu developer slug
curl -fsSL https://alexdundes.github.io/yoda/install/yoda-install.sh | sh -s -- --root . --dev mynick

Executa um script remoto. Em ambiente sensível, revise antes e prefira a versão fixada.

Falta um passo, e ele é o que faz o agente enxergar o YODA: aponte o arquivo de entrada do seu agente para o manual embarcado. Em um projeto com CLAUDE.md, AGENTS.md ou GEMINI.md na raiz, acrescente:

Os três modos

Cada modo tem uma postura

YODA não é um fluxo único. São três modos com objetivos distintos, e eles não se misturam: entra-se e sai-se de cada um explicitamente. Você diz em qual quer entrar, e o agente assume as restrições daquele modo.

criar

YODA Intake

Transforma demanda solta em issue executável. Revisa o backlog, coleta issue externa quando existe, lê a documentação-base e fecha o escopo. Nada é implementado aqui.

executar

YODA Flow

O ciclo de execução: Study, Document, Implement e Evaluate. Uma fase por interação, com entregável apresentado e parada obrigatória no fim de cada uma.

preparar

YODA Prep Flow

Amadurece uma issue específica até o Document, sem autorizar implementação. Útil quando o melhor trabalho de hoje é deixar a issue menos nebulosa.
