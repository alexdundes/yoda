YODA Intake

O modo em que uma demanda solta vira uma issue executável. Aqui nada é implementado: o resultado é um contrato de trabalho fechado o suficiente para ser executado depois.

Quando usar

Sempre que existir trabalho a fazer e ainda não existir issue para ele. Serve tanto para o pedido que chegou pronto quanto para o desabafo em texto corrido — a tradução para estrutura é justamente o trabalho do modo.

Você diz

“Vamos entrar no YODA Intake.”

“Entra no Intake. A listagem de pedidos está lenta desde que ligamos o cache novo, e eu suspeito que a invalidação esteja errada.”

O que acontece

O agente executa o script de Intake e segue o runbook devolvido por ele. O roteiro varia conforme exista ou não uma fonte externa, mas a espinha é sempre a mesma.

Fonte externa

O agente pergunta se a demanda tem uma issue em outro sistema. Se tiver, ele coleta o conteúdo e guarda um JSON local, informando qual transporte foi usado.

Documentação-base

Pergunta se já existe documentação no projeto que fundamenta a demanda. Pode ser um arquivo ou uma pasta, e pode ser qualquer artefato: análise técnica, planilha, contrato, nota de reunião. Se existir, o agente lê antes de fechar a issue.

Revisão do backlog

Antes de criar qualquer coisa, o agente olha o que já existe e aponta o que a demanda tem de sobreposição com issues anteriores. Evita duplicata e evita reabrir decisão já tomada.

Tradução em estrutura

A conversa vira Summary, Context, Objective, Scope, Out of scope, Requirements, Acceptance criteria, Entry points, Tests e Risks. É aqui que a demanda deixa de ser lembrete e vira contrato.

Criação e apresentação

O agente cria o arquivo, preenche as seções e apresenta o resultado. Ao final, propõe entrar no YODA Flow — mas não entra sozinho.

Prioridade é exceção, não ranking

Toda issue nasce com prioridade 5, e o normal é que continue assim. A ordem de execução vem da ordem natural: retoma a issue em andamento, adia as que têm dependência não resolvida, e depois segue a ordem estável dos IDs.

Prioridade só muda como exceção justificada: acima de 5 para rodar antes, abaixo de 5 para rodar depois, sempre com o motivo relativo registrado na própria issue. “É importante” não é motivo suficiente — quase tudo é.

Para sequência real de execução, o instrumento certo é depends_on, e só quando uma issue de fato não pode ser executada corretamente antes de outra. Dependência artificial para organizar backlog atrapalha a seleção determinística.

O que o Intake não faz

Não implementa

Nenhuma linha de código sai daqui. Se a conversa derivar para “já que estamos nisso”, o modo está sendo violado.

Não decide sequência por prioridade

Criar um lote de issues com prioridades decrescentes para simular ordem é uso errado do campo. A ordem vem da criação e das dependências reais.

Depois do Intake

Executar a issue pelo YODA Flow, uma fase por vez.

Ou apenas amadurecer

Preparar a issue até o Document sem autorizar implementação.
